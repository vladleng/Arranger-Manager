# Arranger Manager — развитие в экосистеме MR

**Решение 2026-10-28:** связь со Studio Pro упразднена. Первый музыкальный источник — **MR Live**, затем **MR Studio**. Страницы, задачи, план дня, календарь, Timeline, аналитика и GPT сохраняются в плане. [Решение и проверенные sources/assets](MR-ECOSYSTEM.md); родитель #36.

## База и последовательность

0.1e–0.1g приняты и слиты в main (PR #43–#45). Кандидат 0.1h / PR #46 — раскрывающиеся задачи, чек-поинты, Notes и ПКМ; функциональный source 9caea589, Windows Build #74 ранее прошла 8/8 наборов. Приёмка 0.1h не получена. Этот пересмотр не является её приёмкой или реализацией MR-интеграции.

Ближайший порядок: довести назначенный срез 0.1h → MR UDS #47 и вывод Studio Pro зависимости #7 с сохранением данных → новый 0.1i / MR Live #48 → 0.1j / приёмка 0.2. После первого принятого Live-контракта отдельно подключить MR Studio #49. Его точный выпуск не назначен и первая Live-связь от него не зависит.

| Этап | Выпуск | Результат | Issue |
| --- | --- | --- | --- |
| 1 | 0.2 | Общее пространство; MR-дизайн, legacy continuity и первый MR Live adapter | #37, #47, #7, #48 |
| Отдельное продолжение после Live | не назначен | MR Studio на общем слое источников | #49 |
| 2 | 0.3 | План дня из общих задач | #38 |
| 3 | 0.4 | Календарь всех страниц | #39 |
| 4 | 0.5 | Timeline проектов по датам | #40 |
| 5 | 0.6 | Аналитика подтверждённых соцсетей | #41 |
| 6 | 0.7 | GPT-помощник / подключение по выбранному пути | #42 |

Этапы 2–6 сохраняют порядок. Календари и Timeline зависят от общей модели дат, аналитика — от ядра и подтверждённого доступа, GPT — от ядра/команд и реальных данных. Не запускать все направления автоматически.

| Подэтап | Работа / состояние |

| 0.1f — навигация | Принят: страницы, иерархия без циклов, архив, Shell/Commands/Queries/Controller. DAW-раздел — существующее legacy представление. |

| 0.1h — общие задачи | Кандидат PR #46: один owner/ID, свойства/P1–P4/Notes, чек-поинты, описание, раскрытие и ПКМ, архив/восстановление. Требуется приёмка; MR-дизайн отслеживается отдельно в #47. |
| MR UDS / legacy continuity | #47 — scoped Manager Kit из MR-Studio, реальные динамические значения и один визуальный язык. #7 — вывод Studio Pro reader/Hub/ARA зависимости без потери локальных данных и backups. Это запланировано, не сделано текущими docs. |
| 0.1i-A — контракт MR Live | #48: native model/commands, IDs и владельцы, версии/ревизии, статусы, progress, Browser saved vs working item, повторные setlist references. Не путать layout/demo/native show и не объявлять публичный API существующим. |

| 0.1i-C — команды источника | Отдельный срез #48, если нужен write-back: commands/IPC, revision guard, Undo/save/recovery. Read-only MVP не считается завершённой двусторонней связью. Не менять открытый show сторонней записью целого файла. |
| 0.1j — поиск/переносимость/приёмка | Страницы, задачи и source references, экспорт/импорт IDs/blocks/Notes/связей, конфликты, relink, backup/restart. Старые локальные задачи доступны без Studio Pro. Проверка выбранного Live-среза и пользовательская приёмка 0.2. |

**Критерии:** старые данные и ID сохранены; обычные задачи и MR Live links не дублируются; фактические границы read-only/write-back видны; экспорт/импорт/recovery проверены. Статус и progress не смешиваются, новые документы/схемы не заявляются поддержанными без проверки.

**MR Studio:** #49 после первого проверенного Live-контракта, без нового task backend или audio engine. Экспорт Studio → Live Playback (MR-Studio#291) — другая задача.

Принятый JSON/JUCE выбор не отменяется сменой источника. [WORKSPACE-0.1e-DECISIONS](WORKSPACE-0.1e-DECISIONS.md) — историческое решение хранилища, [WORKSPACE-ARCHITECTURE](WORKSPACE-ARCHITECTURE.md) — действующие границы.

## Этап 2 — План дня из общего списка задач, выпуск 0.3

Issue: [#38](https://github.com/vladleng/Arranger-Manager/issues/38). Зависимости: Этап 1 / 0.2.

**Результат:** Выбирать реальные задачи из общего списка на день и видеть их выполнение с переходом к странице задачи или песни.

| Подэтап | Работа |
| --- | --- |
| 0.2a — Даты и представление Сегодня | Добавить плановый интервал (дата без времени или дата+время), необязательный дедлайн и часовой пояс рабочего пространства. Сегодня выбирает незавершённые задачи из всех страниц по попаданию планового интервала в день; просроченные дедлайны показывать отдельно. День по умолчанию Asia/Krasnoyarsk, настройка доступна. |
| 0.2b — Планирование из списка | Добавление существующей задачи в выбранный день меняет её плановый интервал; список показывает источник. Перенос на завтра меняет даты, а снятие с плана очищает плановый интервал, сохраняя задачу. Не делать отдельный статус выполнения дневной копии. |
| 0.2c — Порядок и фокус | Ручной порядок в дне хранится как список ID, фильтр страницы/проекта, поиск незапланированных задач. Чек-поинты в общем обзоре свёрнуты в родителя; их отдельное планирование не вводится без отдельного решения. DONE отражается во всех представлениях; progress музыкального источника обновляется только по принятому контракту #48/#49. |
| 0.2d — История и приёмка | Хранить фактическое completedAt и изменения статуса, различать план и факт. Раздел завершённых задач дня, устойчивые ссылки при архивировании и переход через полночь, перезапуск и Windows CI. Выпуск 0.3 после приёмки. |

**Приёмка:** Одна связанная задача MR Live и одна обычная задача планируются на день, переносятся, выполняются и открываются из Сегодня без копий; часовой пояс, многодневные интервалы и просрочки обработаны.

**Перед реализацией:** Повторяющиеся задачи, системные напоминания и автоматический подбор загрузки — расширения после основного сценария; не включать скрыто в первую итерацию.

## Этап 3 — Общий календарь всех страниц, выпуск 0.4

Issue: [#39](https://github.com/vladleng/Arranger-Manager/issues/39). Зависимости: Этап 2 / 0.3.

**Результат:** В одном календаре видеть задачи и события всех страниц, открывать источник и изменять общие даты.

| Подэтап | Работа |
| --- | --- |
| 0.3a — Модель календаря | Календарь строится по тем же плановым интервалам задач; дедлайн отдельный маркер. Добавить календарное событие со своим ID, страницей, началом/концом и признаком весь день: репетиция/выступление может не быть задачей. План задач и события не изменяют музыкальное время и progress источника сами по себе. |
| 0.3b — Месяц и неделя | Общий календарь по всем страницам; месяц, неделя и список событий дня. Цвет/источник страницы, фильтры, переход к задаче/источнику MR/странице. Задачи без даты остаются в общем списке. |
| 0.3c — Изменение дат | Создание события, перенос и изменение длительности в календаре; изменения задач отражаются в Сегодня и списках. Интервалы без времени, многодневные записи, границы суток и отмена изменения; не подменять дедлайн плановой датой. |
| 0.3d — Приёмка календаря | Проверить общий календарь двух обычных страниц и ссылки на Live item, часовой пояс, пересечения, перезапуск, отсутствие дубликатов и Windows CI. Выпуск 0.4. |

**Приёмка:** Календарь собирает все страницы, drag даты изменяет исходную запись, Сегодня и списки обновляются; событие и задача различимы.

**Перед реализацией:** Google Calendar, CalDAV и двусторонняя синхронизация внешних календарей — отдельное будущее расширение; общий календарь внутри приложения не требует внешнего сервиса.

## Этап 4 — Timeline для планирования проектов, выпуск 0.5

Issue: [#40](https://github.com/vladleng/Arranger-Manager/issues/40). Зависимости: Этап 3 / 0.4.

**Результат:** Показывать проекты и задачи полосами по датам, менять сроки и оценивать последовательность работ.

| Подэтап | Работа |
| --- | --- |
| 0.4a — Представление интервалов | Timeline использует плановые даты задач и событий из календаря. Группировка по странице/проекту, шкала день/неделя/месяц, статус и источник. Это календарная шкала работ; позиции Live/Studio событий остаются в музыкальном проекте. |
| 0.4b — Перенос и длительность | Перетаскивание полосы и её краёв меняет общий плановый интервал с отменой; календарь и Сегодня обновляются. Задачи без дат показывать в отдельном списке для планирования. |
| 0.4c — Этапы и связи | Добавить веху проекта без длительности и связи предшественник → следующая задача; отказ от циклов. Показывать пересечения и нарушенные зависимости. Первоначально не переносить цепочку сроков автоматически. |
| 0.4d — Приёмка Timeline | Проверить проект из нескольких задач и связанный Live item, календарную согласованность, масштаб/прокрутку, длительности, циклы и Windows CI. Выпуск 0.5. |

**Приёмка:** Изменение полосы обновляет исходную задачу и календарь; вехи и зависимости сохранены; музыкальное время клипа не принимается за дату проекта.

**Перед реализацией:** Автоматическое перепланирование, учёт ресурсов и тайм-трекер фактических часов — отдельные расширения, не обязательная часть первого Timeline.

## Этап 5 — Сбор и обзор аналитики соцсетей, выпуск 0.6

Issue: [#41](https://github.com/vladleng/Arranger-Manager/issues/41). Зависимости: Этап 1 / 0.2; по порядку после 0.5. Интеграционный слой используется этапом 6..

**Результат:** Собирать подтверждённые метрики подключённых каналов и публикаций, показывать историю и связывать публикации с задачами контента.

| Подэтап | Работа |
| --- | --- |
| 0.5a — Источники и проверка доступа | Выбрать с пользователем первые аккаунты/платформы; кандидаты из рабочего контекста — YouTube и VK. По текущей официальной документации проверить доступные метрики, права, лимиты, стоимость и способ авторизации на реальном тестовом аккаунте. Зафиксировать матрицу возможностей; недоступные метрики не обещать. |
| 0.5b — Общий слой интеграций | Адаптер источника, безопасное локальное хранение токенов, подключение/отключение, состояние доступа и ручное обновление. Фоновые запросы без блокировки UI, таймауты, повтор после ошибок/лимитов, время последней успешной загрузки. Не встраивать секреты в exe или экспорт. |
| 0.5c — Первый источник | Реализовать один подтверждённый адаптер: аккаунт, публикации и доступные метрики. Сохранять исходные идентификаторы, измеренные даты/периоды, единицы и источник; повторная загрузка не дублирует записи. CSV/ручной импорт допустим как явно помеченный способ, если API не предоставляет нужные данные. |
| 0.5d — Дашборд и связи с контентом | Графики по периоду, динамика и сравнение публикаций только по сопоставимым метрикам. Отдельно накопительные значения и показатели периода; нет данных не равно нулю. Связать публикацию со страницей/задачей контента. Рекомендации в будущем отделять от измеренных фактов. |
| 0.5e — Второй источник и приёмка | Добавить второй подтверждённый источник либо явно согласованный перенос его реализации; проверить повторную загрузку, отозванный доступ, отсутствие сети, устаревшие данные, экспорт истории без токенов. Настроить обновление при работающем приложении, Windows CI и выпуск 0.6. |

**Приёмка:** Работает минимум один реальный источник с историей, проверенными единицами/периодами и ссылками на публикации; состав источников явно принят пользователем, данные не выдуманы; ошибки не мешают локальным задачам.

**Перед реализацией:** Площадки/аккаунты, метрики и автоматический сбор при выключенном приложении определить до реализации соответствующей функции. Последний потребует отдельного постоянно работающего сервиса. Автопубликация в соцсетях не входит в сбор аналитики.

## Этап 6 — Интеграция с ChatGPT и помощник по рабочему пространству, выпуск 0.7

Issue: [#42](https://github.com/vladleng/Arranger-Manager/issues/42). Зависимости: Этап 1 / 0.2 и слой интеграций этапа 5; для анализа соцсетей — реальные данные 0.6..

**Результат:** Работать с контекстом страниц, задач, песен и аналитики через выбранную GPT-интеграцию; получать план и применять проверенные изменения к единым задачам.

| Подэтап | Работа |
| --- | --- |
| 0.6a — Сценарий и способ интеграции | Выбрать основной путь: помощник внутри приложения через OpenAI API или доступ ChatGPT к данным/командам приложения через MCP/подключение. Допустимы оба по очереди. Проверить актуальную документацию, доступ аккаунта, размещение, авторизацию и затраты; не предполагать автоматический доступ к истории личных чатов. |
| 0.6b — Контекст и инструменты | Выбор страниц/периода аналитики, чтение задач/песен и поиск через доменные команды. Формат предложений на создание задач/чек-поинтов и изменение плана; ссылки на исходные записи. Минимальный выбранный контекст, отсутствие токенов соцсетей в запросах, журнал действий. |
| 0.6c — Помощник внутри приложения — если выбран API | Чат с контекстом выбранной страницы, план дня, декомпозиция задач, сводка прогресса подключённых MR-источников и фактической аналитики. Настраиваемый провайдер/модель, отмена запроса, лимит расхода и ошибки сети. API-ключ/авторизация по поддерживаемому официальному способу; не считать подписку ChatGPT автоматически API-доступом. |
| 0.6d — Подключение приложения к ChatGPT — если выбран этот путь | MCP-инструменты поиска/чтения и ограниченных изменений задач через тот же доменный слой. Проверить поддерживаемый способ подключения и доступность для аккаунта; отдельно решить локальный мост или размещённый сервис. Не обращаться напрямую к файлу базы из внешнего клиента. |
| 0.6e — Применение предложений и приёмка | Предпросмотр изменений, подтверждение применения, проверка актуальной ревизии, отмена и отсутствие дублей при повторе запроса. Отделять вывод модели от источников аналитики; проверить сценарии нет данных, отмены и истёкшего доступа. Выпуск 0.7 после проверки хотя бы одного выбранного пути; второй путь остаётся явно отмеченным расширением. |

**Приёмка:** Выбранный путь GPT работает с реальными записями; предложение плана/задач можно проверить и применить без дублей; GPT не переписывает файлы источников напрямую и использует только подтверждённые команды владельца; ошибки интеграции не блокируют обычную работу.

**Перед реализацией:** Способ интеграции и модели не утверждены. Этот этап планируется, API-ключи и аккаунты сейчас не запрашиваются. Второй способ интеграции не объявляется реализованным при выпуске первого.

## Ограничения и снятые направления

- Studio Pro/.song/.show, writer и ARA/context bridge не развиваются. #19 закрывается not planned; закрытые исследования #8/#18 не переоткрываются. Legacy runtime выводится через #7, не этим docs-only изменением.
- Сохранность старого каталога, task/checkpoint IDs, Notes keys, статусов, порядка и backups обязательна. Не удалять пользовательские файлы и не терять задачи при отсутствующем .song.
- MR UDS Manager assets, Live browser demo и native runtime имеют разные статусы принятия/публикации. Ревизии проверены в MR-ECOSYSTEM; макет не является native API.
- #35 — мобильный доступ и синхронизация отложены; использовать общее ядро и MR references в будущем, без отдельной базы песен.
- Notion compatibility, совместная работа, внешние календари, автопубликация, автономные GPT-действия и автоматическое перепланирование не входят скрыто в эти этапы.
- Исторические HYBRID/HUB/ARA документы сохранены; их Studio Pro сценарии не являются текущими критериями выпуска.
