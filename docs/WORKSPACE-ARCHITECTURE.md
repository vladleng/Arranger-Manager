# Рабочее пространство — модель и границы реализации

**Состояние 2026-10-02:** 0.1e и 0.1f приняты и слиты в main (PR #43/#44). Блочный редактор 0.1g — кандидат в PR #45; общие задачи 0.1h и следующие подэтапы не реализованы. Ниже концептуальная модель всего плана, а текущие детали редактора — в разделе 0.1g. Техническая база: JUCE/C++20 и версионированный JSON. Решения: [WORKSPACE-0.1e-DECISIONS](WORKSPACE-0.1e-DECISIONS.md); проверка: [HYBRID-0.1g](HYBRID-0.1g.md).

## Сценарий пользователя

Пользователь создаёт страницу проекта (аранжировка, контент или обычная работа), пишет описание и создаёт задачи. Открытая задача имеет подробную страницу с описанием и чек-поинтами. Он планирует её на день, видит в общем календаре и на Timeline. Выполнение задачи отражается во всех представлениях, а у задачи песни — в её DAW-прогрессе. Страница контента может ссылаться на публикацию и её реальные метрики; GPT использует выбранные страницы и метрики для предложений.

## Единые записи, разные представления

| Сущность | Основные поля/связи | Правило |
| --- | --- | --- |
| Workspace | id, имя, timezone, версия схемы | Локальное рабочее пространство, основная работа доступна без сети |
| Page | id, parentPageId, заголовок, тип, порядок, archivedAt | Обычная страница, страница проекта/контента/песни; вложенность без циклов |
| Block | id, владелец (страница или описание задачи), тип, содержимое, порядок | Сначала текст, заголовок, список, чек-лист, ссылка; порядок и ID сохраняются |
| Task | id, ownerPageId, имя, статус, приоритет, Notes, описание из блоков, порядок, даты, completedAt, revision | У задачи одна страница-владелец; список/Сегодня/календарь/Timeline ссылаются на этот ID |
| Checkpoint | существующий id, parentTaskId, имя, статус, Notes, порядок | Первоначально один уровень внутри задачи; сохраняются прежние правила прогресса |
| SongLink | id песни, pageId, путь .song, локальный статус/тип, Notes, снимок/ошибка чтения | ID не зависит от пути; перемещение файла не создаёт другую песню |
| CalendarEvent | id, pageId, название, плановый интервал, описание | Событие может существовать без задачи; не повышает прогресс песни |
| View | id, вид, фильтр, порядок/группировка | Представление общих записей, не независимый список задач |
| ExternalAccount / Publication | provider, nativeAccountId/nativePublicationId, URL, время публикации, ссылка на страницу/задачу | Внешние ID и источник сохраняются; повторная загрузка не создаёт дубль |
| MetricObservation | аккаунт/публикация, metricKey, значение, единица, период, observedAt, источник, качество/доступность | Накопительные и периодические метрики не смешиваются; отсутствие данных не равно нулю |
| Change / Proposal | entityId, revision, команда, время, источник изменения | Проверяемые изменения от UI/интеграций и применяемые предложения GPT |

Это концептуальная модель всего продукта. В принятой 0.1e реализованы workspace, pages/blocks и catalog schema 2; остальные сущности добавятся по плану. В принятой 0.1d JSON songCatalog v1 содержит песни по пути и вложенные задачи. 0.1e переносит их в workspace schema 1: у песни отдельные id/pageId, задачи хранятся один раз и принадлежат странице песни. Задача может открываться как подробная страница через тот же редактор блоков; не создавать второй объект задачи или несвязанный текстовый дубль её свойств.

## Даты и прогресс

Плановый интервал задачи: начало и конец либо как даты без времени, либо как дата+время с зоной/UTC-представлением. Единую точную семантику границ выбрать в 0.2a и проверить на стыке суток. Дедлайн — отдельное поле. Завершение — фактическое completedAt; изменение плана не меняет дату фактического выполнения.

Сегодня выбирает задачи, чей плановый интервал пересекается с выбранным днём в timezone рабочего пространства; отдельно показывает просроченные дедлайны. Добавить из списка на день означает записать плановый интервал исходной задачи. При смене дня сохраняется исходная задача; действие «снять с плана» очищает плановые даты, а не удаляет запись. Порядок дневного представления хранится по ID. Многодневная задача может встречаться в нескольких днях, но имеет один статус. Календарь и Timeline используют эти же даты; изменение в одном виде отражается в других.

Общий календарь включает все активные страницы с фильтрами. Timeline группирует задачи/события по странице/проекту и показывает календарные интервалы, а не музыкальное положение AudioEvent/MusicPart. Чек-поинты в первом общем обзоре остаются внутри родителя; автоматическое планирование каждой подзадачи не требуется. Текстовый чек-лист в блоках не равен Checkpoint с ручным статусом.

Для новых обычных задач использовать действующий набор статусов; DONE — завершение. Приоритет P1–P4 хранится локально у задачи и отдельно у песни, когда реализован, и не читается из имени клипа. Перевод в DONE не должен автоматически завершать родителя. Задачи из другой страницы не считаются в PROG песни; песенные задачи должны сохранять явное владение/связь с песней. Перемещение такой задачи между страницами требует явной политики изменения её участия в PROG, а не скрытого дублирования.

## Архитектура приложения

В 0.1f выделены WorkspaceCommands (создать/переименовать/переместить/архивировать/восстановить обычную страницу), WorkspaceQueries, WorkspaceController (проверка и сохранение до замены модели) и WorkspaceShell. WorkspaceStore и read-only DAW reader остаются отдельными слоями. Доменные команды статусов/дат и интеграций добавятся в следующих подэтапах. UI, GPT и интеграции вызывают одни команды с проверкой идентичности и актуальной ревизии. Не держать вторую базу задач в календаре, GPT или мобильном клиенте.

Переход от JSON настроек к хранилищу рабочего пространства реализован в принятой 0.1e. Сравнение версионированного документа и SQLite зафиксировано в WORKSPACE-0.1e-DECISIONS.md; для этапа 1 выбран отдельный JSON-документ. SQLite остаётся вариантом для больших объёмов аналитики. Не растить ApplicationProperties в неограниченную историю метрик и блоков. Настройки окна/выбранных представлений отделить от пользовательских записей.

Текущий JUCE UI и код чтения .song сохраняются как рабочая основа этапа 1. В 0.1e доступны native/web-прототипы блоков; визуальная пользовательская оценка ещё предстоит. Решение о другом UI-стеке документировать до переписывания. Reader не должен зависеть от календаря или соцсетей. VST3 сохраняет свой ограниченный DAW-сценарий; страницы, аналитика и GPT ориентированы прежде всего на desktop, полное повторение их в плагине не требуется этим планом.

## Миграция и переносимость

До первой миграции сохранить копию каталога 0.1d. Переносить папки, песни, ручные статусы/типы, задачи/чек-поинты с их существующими ID, порядок и localNotes. Добавить ID песни, не меняя ключи заметок клипов в ходе обычной миграции. Миграция повторяемая без повторного добавления записей; при ошибке оставить прежние данные читаемыми и дать восстановить резервную копию. Не изменять .song.

Экспорт рабочего пространства включает версию схемы, записи, блоки и связи, локальные Notes и доступные пользовательские данные/историю аналитики. Пути к .song — локальные ссылки, сами проекты и аудиофайлы не копируются автоматически. Импорт проверяет формат, целостность ссылок, конфликтующие ID и повторное связывание путей. Токены/API-ключи не экспортируются. Архивирование страницы/задачи и восстановление сохраняют ID; окончательное удаление определяет поведение ссылок и внешних связей, не удаляет DAW-файл. Прежнее удаление записи каталога в 0.1d уничтожает локальные задачи — перед сменой UX сохранить и проверить эту миграцию.

## Аналитика и внешние интеграции

На этапе 5 выбрать реальные площадки и аккаунты. YouTube/VK — кандидаты, а не уже подтверждённые адаптеры. Для каждой площадки проверять актуальные официальные API и тестовый доступ, отдельно описывать доступные поля, периоды, квоты и ошибки. Сбор аналитики не означает автопубликацию. Если API не даёт нужных метрик, использовать явно обозначенный импорт/ручной ввод либо оставить поле недоступным.

Адаптеры работают вне UI-потока; хранить происхождение данных, единицы, период и время успешной загрузки. Повторный запрос не дублирует публикации/наблюдения. Не складывать сравнимые по названию, но разные по смыслу показатели платформ. Отозванная авторизация и отсутствие сети сохраняют локальные задачи и последнюю аналитику с отметкой устаревания. Сбор при закрытом приложении потребует отдельно выбранного сервиса, не обещать его обычным desktop-таймером.

## ChatGPT: два направления

1. **Помощник внутри приложения.** Выбранные страницы/задачи и данные аналитики передаются в поддерживаемый OpenAI API. Модель предлагает план, чек-поинты и выводы; приложение проверяет структурированное предложение и применяет его через доменные команды.
2. **Приложение как источник и инструменты для ChatGPT.** MCP/подключение предоставляет поиск, чтение и выбранные команды рабочего пространства. Конкретный способ связи, размещение и доступность аккаунта проверить перед реализацией. Локальная база сама по себе не становится доступной удалённому ChatGPT.

Основной путь выбрать в 0.6a; внедрение обоих не является обязательным условием первой 0.7. Не считать подписку, историю личного ChatGPT и API одним механизмом доступа. Не обещать чтение всех старых чатов пользователя. Доступ к ключам и расходы проверить при реализации; конкретная модель не закрепляется сейчас.

Контекст выбирается пользователем: страницы, задачи, песни, период аналитики; токены внешних аккаунтов в него не включаются. GPT-ответ отделять от измеренных фактов и давать ссылки на исходные записи. Предложение изменения показывает конкретные задачи/даты до применения; применение проверяет ревизии, журналируется и допускает отмену. Повтор запроса не создаёт дублей. Внешние публикации и текст страниц — данные для анализа, не команды на произвольное выполнение. .song остаётся read-only и для GPT.

Основание технических вариантов (официальные документы, проверены 2026-10-02; повторно проверить при реализации):

- [OpenAI API — Using tools](https://developers.openai.com/api/docs/guides/tools): инструменты и функции в запросах Responses.
- [MCP server and UI quickstart](https://developers.openai.com/plugins/build/app-quickstart): MCP-сервер и подключаемый интерфейс для ChatGPT.

## Границы оболочки 0.1f

Обычные страницы редактируют только свои заголовки, вложенность и архив. Песни/папки каталога по-прежнему управляются в DAW. Все задачи — read-only запрос существующих задач песни по их ID, с переходом к редактированию в DAW. В 0.1f блоки показывались для чтения; кандидат 0.1g добавляет редактор обычных страниц. Архив родителя наследуется потомками, а собственные архивные отметки ребёнка сохраняются при восстановлении родителя. Выбранный раздел — UI-настройка, не поле пользовательских записей.

## Реализация кандидата 0.1g

BlockEditor — переиспользуемый UI с callbacks документа; BlockEditorSession хранит черновик и историю массива блоков отдельно по document ID, без снимков всего workspace. Запись страницы через WorkspaceCommands::replacePageBlocks требует исходные blocks, проверяет владельца/архив/валидность и проходит WorkspaceController. Конфликт сохраняет черновик. Undo/redo не меняет DAW-каталог или блоки другой страницы.

WorkspaceBlock.name — необязательное строковое имя, schema 1 без изменения номера; старый документ без name получает пустую строку. Существующие ID/порядок и типы совместимы. Автосохранение 500 мс, flush до навигации/команд/закрытия, история до 100 групп только на текущий запуск. Подробнее HYBRID-0.1g.md. Общие задачи и привязка их описаний — 0.1h; один и тот же компонент получает другое Read/Write binding.
