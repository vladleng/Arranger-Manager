# Arranger Manager 0.1a — проверка записи копии `.song`

Это первый технический шаг этапа 3. Основное приложение пока показывает сохранённый проект как раньше. Прилагаемый `edit_song_copy.py` меняет **одно имя клипа в новом файле-копии**. Он не изменяет исходный `.song` и не записывает в открытый проект Studio Pro. Для этой проверки на Windows требуется Python 3.10+.

1. Закройте тестовый проект в Studio Pro. Выберите небольшую тестовую `.song` и сохраните её собственную резервную копию.
2. Получите точные `trackID`, `start`, `length`, `timeFormat` и имя нужного клипа: `python read_song_inventory.py "C:\Songs\Test.song" -o inventory.json`. Пустой или отсутствующий `timeFormat` означает, что ключ `--time-format` можно опустить.
3. Поменяйте имя одного `AudioEvent` в **новой копии**:

```powershell
python edit_song_copy.py "C:\Songs\Test.song" "C:\Songs\Test-0.1a-copy.song" --track-id "track-1" --type AudioEvent --old-name "WIP | Guitar" --start "32" --length "8" --new-name "DONE | Guitar | Проверить атаку"
```

4. Аналогично проверьте `MusicPart` из новой копии в другом новом файле, указав `--type MusicPart` и его собственные атрибуты.
5. Откройте последнюю копию в Studio Pro 8.1.2, проверьте оба имени, клипы и медиа, затем сохраните и откройте повторно. Исходный файл не должен измениться.

Если точных совпадений нет или их несколько, операция отказывает и не создаёт копию. `clipID` можно добавить как дополнительный `--clip-id`, но он не считается уникальным после split/copy. При совпадении имени и временных атрибутов у нескольких событий потребуется дополнительный контекст в следующей версии. Выходной путь должен отсутствовать; утилита проверяет ZIP, XML, контрольные суммы остальных записей и неизменность исходного файла.

После проверки копии этап продолжится в 0.1b: выбор клипа и подготовка правки из интерфейса приложения. Прямую запись в оригинал включать только после проверки копии в Studio Pro и отдельной защиты от открытого проекта и изменившегося файла.
